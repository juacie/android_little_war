# 方陣戰鬥構想（討論中，未定案）

> 這份文件記錄 2026-08-15 一輪 playtest 回饋衍生出的設計構想。**不是承諾的規格，是還沒拍板的方向**，開工前要先回來這裡確認範圍，不要直接照單全收動手做。跟目前已完成的 M001 原型（見 [BattleSystem.md](BattleSystem.md)）比，這是核心資料模型等級的改動，不是小修小補。
>
> **狀態更新（2026-08-15）**：下方「核心構想」列的項目中，血量池化、人數上限（固定值，非成長曲線）、比例戰力衰減、方陣內領袖加成（範圍收窄成限定同方陣）**Phase 1 已實作完成**，見 [BattleSystem.md](BattleSystem.md)「Squad model」一節與 [ROADMAP.md](ROADMAP.md)。**移動機制 Phase 2 也已完成，但範圍縮小成 3×5 macro grid 上一次一格**（不是本文件原本設想的 5×5 細格移動——那需要下面「不同兵種一次移動的細格數不同」這種還沒拍板的成長曲線系統），見 [BattleSystem.md](BattleSystem.md)「Movement」一節。英雄兵種、全軍領袖離場改版、5×5 細格移動**仍是未拍板、未開工**的後續階段，以下內容維持原樣供之後規劃參考。
>
> **Phase 2 playtest 回饋（2026-08-15 同日）**：實際玩起來會覺得「像回合制、前排死了後排才移動」，診斷出兩個原因疊加：(1) macro grid 上同側方陣不能疊格，`Movement.planStep` 優先縮短縱深，同一路（同 column）的後排方陣常常要走的下一格正好被自己前排佔著，卡到前排死掉騰出格子才能動；(2) 更根本的是，**目前 `Squad`（見 `Squad.kt`）內部完全沒有代表個別成員（雜兵）的資料結構**——`capacity` 只是攻擊力/血量的乘數係數，不是真的有人在方陣內部 5×5 細格裡各自佔位、跑位。所以就算解掉 (1) 的卡格問題，畫面呈現的仍會是「整個方陣圖示瞬移一格」，不會有雜兵個別移動、方陣隨傷亡稀疏化的視覺效果——那個效果要等下面的 5×5 細格移動真正上線、且方陣內有個別成員實體之後才會出現。(1) 是可以獨立修的小範圍問題（改 `Movement.planStep` 卡格時的 fallback 邏輯），(2) 則跟本文件「還沒定案的問題」裡的方陣成長曲線、5×5 細格是同一個尚未拍板的後續階段。

## 起點：四點 playtest 回饋

1. 進關卡前應該能看到敵方陣容，方便搭配己方陣型。
2. 射程不夠時應該可以移動，而不是原地 idle。
3. 排兵佈陣階段應該限制各兵種數量上限，避免同兵種堆疊破壞平衡。
4. 現在的戰鬥畫面觀感是「你打我、我打你」，缺乏臨場感／兵團感。

討論到第 2、4 點時，範圍逐漸擴大成一個更大的構想：把整個戰鬥模型從「一格一人」換成「一格一個方陣」。

## 核心構想：方陣制

- 陣型的每一格（目前 3×5 macro grid 的一格）不再是單一戰鬥單位，而是一個**方陣**，內部再切成 5×5 的細格，最多容納 25 人。
- 方陣人數隨等級成長，走完全平方數的上限：**1 → 4 → 9 → 16 → 25**，視覺上方陣會長成越來越大的正方形。**但每個兵種對應的成長曲線不會一樣**（例如騎兵可能天生方陣上限就比較小，步兵可能比較大），這直接牽動平衡性，不能套一條通用曲線就定案，之後要逐兵種個別測試才能拍板實際數字。
- 血量演算改成**方陣總血量**（而不是單一角色血量），方陣被打光才算陣亡。
- 每個方陣有一位**核心人物，也就是「方陣領袖」**，數值跟同方陣裡其他小兵不同（通常更強），讓方陣看起來有辨識度，不是一群數值全部一樣的雜兵堆疊。
- **全軍領袖**（對應 GDD §6 現有的領袖概念，但規則改變）：**沒有血量，不上 3×5 戰場**，純粹提供整個陣容某方面的特殊加成，不是會被打死或會攻擊的戰鬥單位。這跟現行 `isLeader` 的實作不同——目前的領袖是掛在一個會上場、佔格子、有血量的戰鬥單位上（見 [BattleSystem.md](BattleSystem.md)「領袖 aura」一節），改成場外純 buff 來源後，這部分的資料模型跟 UI（陣容編輯時要有獨立於 3×5 格子的「全軍領袖」欄位）都要跟著動。
- **戰力隨殘存人數比例衰減**（類似 Total War 的單位模型）：方陣裡人越少，攻擊力／命中率等數值等比例打折，藉此演出「兵團被磨損、越打越弱」的過程，而不是一整組人共用一條血條、戰力卻恆定到打光那一刻才驟降。這點已經跟使用者確認要採用比例衰減模型。
- 移動改用細格（5×5 sub-grid）計算距離，不同兵種一次移動的細格數不同（例如騎兵一次跨多格、重步兵一步步挪）。
- **移動共用現有的攻速能量閘門**：輪到某方陣行動（energy ≥ 100，消耗規則不變）時，如果範圍內沒有可打的敵人，就把這次行動改成「往目標方向移動」而不是「攻擊」，一樣消耗 100 能量。這樣攻速快的方陣天生移動也快，不用額外定義一個 `moveSpeed` 數值，直接重用 `attackSpeed`，維持 data-driven 的一致性。移動方向的選擇是確定性規則（往可縮短 distance 的方向走），不引入額外 RNG，戰鬥模擬的 determinism 不受影響。

- **英雄**是另一個獨立的兵種分類（跟近戰／弓兵／法師等現有兵種同一層級，不是「方陣領袖」的另一種說法）：
  - 英雄自成一個方陣，方陣裡永遠只有他一人，不會像一般方陣隨等級長到 4/9/16/25。
  - 因為方陣裡只有自己，他天生同時是小兵也是自己方陣的領袖，不需要另外定義「方陣領袖 vs 小兵」數值差異（那只在多人方陣裡才需要）。
  - 加成範圍偏向全陣容，比一般方陣領袖（只影響自己方陣）更廣。
  - 每次編隊最多可以上場 **3 位英雄**。
  - 英雄本質上就是「方陣領袖」的一種（只是方陣固定 1 人）——跟一般方陣領袖是同一種角色機制，差別只在所在方陣人數。
  - 在角色收集／抽角色系統裡，英雄不會特別跟其他兵種區分（同一個池子抽），區分只發生在**部署上陣**這一步（該兵種類別上限 3 位）。
  - 跟「全軍領袖」是完全不同層級：全軍領袖沒血量、不上場、只給場外加成；英雄是會上場戰鬥、佔一個方陣格位的戰鬥單位。兩者不衝突、會同時存在。

## 這跟現有文件衝突的地方

`docs/BattleSystem.md`「已知的刻意簡化」目前列了兩條會被這個構想推翻的決定：

- 「No movement...range and formation composition are meant to be the puzzle」
- 「1 formation slot = 1 combatant（GDD 的『一格 N 人』方陣構想暫緩）」

如果之後真的要做，這兩條要一起改寫，並補上方陣制底下新的 distance／AoE／determinism 說明。

## 附帶的兩個小範圍項目（跟方陣制本身無關，可以獨立做）

- 進關卡前預覽敵方陣容（UI + 讀 `StageData.enemyFormation`，不動引擎）——已完成，commit 09c5718
- 排兵佈陣階段限制各兵種數量上限（Formation 邏輯層 + 可能的 data-driven 上限設定）——**已完成**：`UnitDefinition.formationCap`（data-driven，`null` = 不限制，見 `milestone-001.json`）在 `FormationRepositoryImpl.toggleUnitAt` 放置當下擋掉超過上限的 tap，陣容不變；`FormationScreen` 兵種選單同步顯示「已放置數／上限」。這是排兵佈陣階段的格數限制，跟方陣制構想裡的 `squadCapacity`（單一方陣內部人數）是不同層級的數字，兩者不衝突。

## 還沒定案的問題

- 殘存人數比例怎麼影響戰力：線性衰減、還是有門檻（例如低於某比例才開始掉）？
- 各兵種的方陣人數成長曲線（1/4/9/16/25 這條上限對每個兵種實際會落在哪幾階）要逐兵種測試後才能定案，不是通用數字。
- 方陣核心人物的數值跟一般小兵差多少、用什麼公式算（例如小兵數值的固定倍率，還是獨立設定）——也需要之後跟成長曲線一起測。
- 英雄「加成範圍偏向全陣容」的具體規則（buff 全部方陣、還是只 buff 特定範圍內的方陣）還沒定義。
- 全軍領袖改成「場外、無血量、純加成」之後，陣容編輯 UI 要多一個獨立於 3×5 格子的欄位放全軍領袖——這塊還沒設計。
- 「抽角色」這個說法代表未來會有角色收集／抽卡系統，這已經超出 CLAUDE.md 現況明訂的 M001 範圍（「不要在這之前就動手做抽卡...除非使用者明確要求擴大範圍」）。這裡先記下來，不代表現在要規劃抽卡機制本身。
- 方陣內 5×5 細格跟現有 3×5 macro grid 的座標系怎麼疊在一起，AoE（`PLUS` 十字範圍）要在哪一層座標系上算？
- 方陣人數隨等級成長，代表要有某種等級/成長狀態——這塊在 M001「純本機、無持久化」的範圍裡完全不存在，是額外的系統。
- 這個改動量級已經不是「加個功能」，是重寫 battle-engine 的核心資料模型（`BattleUnit` 表示方式、傷害公式、AoE、移動、determinism 全部要動）。建議在 [ROADMAP.md](ROADMAP.md) 裡當成獨立 Milestone 另外排，不要直接塞進正在跑的 M001。
